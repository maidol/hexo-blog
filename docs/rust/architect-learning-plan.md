# 架构师 Rust 学习落地计划（AI 辅助，12 周）

核心是一个固定的学习循环，加上一个循序渐进的项目主线。时间按每天 60～90 分钟、周末 2～3 小时估算，共 12 周，和团队"第 1 个月搭底座、第 2～3 个月试点"的节奏对齐（见 [ai-rust-best-practices.md](ai-rust-best-practices.md) 第七节）。

学习方法一句话：**让 AI 写代码，自己逐行追问"为什么这里要 `Arc`"、"为什么这里需要 `Send`"、"这个生命周期标注表达了什么"。读懂 AI 的代码，是 AI 时代学 Rust 最快的路。**

## 一、核心方法：每段代码都走"预测 → 追问 → 破坏 → 复述"四步

只读 AI 的代码，很容易产生"看懂了"的错觉。四步循环的作用是逼自己真正理解：

| 步骤 | 做什么 | 目的 |
|---|---|---|
| **1. 预测** | 读代码前先写下：这里该用 `&`、`&mut` 还是 move？要不要 `Arc`？会不会出现生命周期问题？ | 暴露自己的理解盲区 |
| **2. 追问** | 对每个"为什么"向 AI 提问（问题模板见第四节） | 获取解释 |
| **3. 破坏** | 亲手删掉 `Arc`、去掉 `move`、改掉生命周期标注、把 `tokio::Mutex` 换成 `std::Mutex`，看编译器怎么报错 | **用编译器验证 AI 的解释**。AI 的解释可能出错，编译器不会 |
| **4. 复述** | 不看代码，用自己的话写一段解释，让 AI 打分并指出错误 | 检验是否真的掌握 |

**第 3 步最重要。** 每个"为什么需要 X"都应该能用一个编译错误来证明。证明不了，就说明这个 X 可能是多余的，AI 写多了（这本身也是 review 能力的训练）。

### 辅助工具（第一周就配好）

| 工具 | 用途 |
|---|---|
| rust-analyzer 的 inlay hints | 在编辑器里直接显示推断出的类型、生命周期省略后的实际标注 |
| `rustc --explain E0502` | 查看任何错误码的详细解释和示例 |
| `cargo expand` | 展开宏，看 `#[tokio::main]`、`#[derive]`、`#[instrument]` 实际生成了什么 |
| Rust Playground | 快速做"破坏实验"，不用建项目 |
| Compiler Explorer（godbolt） | 验证"零成本抽象"：迭代器和手写循环生成的汇编是否一样 |
| `cargo clippy` | 学习地道写法，每条 lint 都有说明链接 |

## 二、项目主线：一个服务，12 周逐步长大

不做零散练习。整个计划围绕一个和团队业务相似的服务展开，比如**短链服务**或**简化版订单服务**，每个阶段给它加一层能力。到第 12 周，这个项目本身就是团队模板仓库的原型。

| 周 | 主题 | 项目进展 | 阶段产出 |
|---|---|---|---|
| 1～2 | 所有权、借用、错误处理 | 命令行版：读文件、解析、统计、输出 | 能独立解释所有权的三条规则 |
| 3～4 | 类型设计、trait、模块 | 抽出 `domain` crate：新类型、状态机 enum、领域错误 | 一份自己设计的领域类型 |
| 5～6 | 并发：线程、`Arc`、锁、channel、`Send`/`Sync` | 加一个多线程后台任务（比如批量过期清理） | 能解释 `Send`/`Sync` 的推导规则 |
| 7～8 | 异步：Future、tokio、axum、sqlx | 变成 HTTP 服务，接入数据库 | 一个能跑的 Web 服务 |
| 9 | 测试和可观测性 | 加上 proptest、insta、tracing、metrics、cargo-mutants | 测试和监控都齐全的服务 |
| 10 | 所有权的极限：图结构、unsafe | 加一个依赖关系图模块（用 arena + slotmap），读懂一段 unsafe 代码 | 能说清楚 arena 和 `Rc<RefCell>` 的取舍 |
| 11～12 | 毕业项目：整理成团队模板 | workspace 拆分、lint、CI、`CLAUDE.md` | **团队模板仓库 v0.1** |

## 三、每周详细安排

### 第 1～2 周：所有权、借用、错误处理

**阅读：** 《The Rust Programming Language》第 1～9 章。

**让 AI 写：** 一个命令行工具，读取日志文件，按状态码统计请求数，输出排行榜。要求用 `Result` 处理错误，不准用 `unwrap`。

**追问重点：**
- 这个函数参数为什么是 `&str` 而不是 `String`？反过来会怎样？
- 这里为什么要 `.clone()`？能不能去掉？
- `?` 运算符展开后是什么？错误类型是怎么转换的？
- 为什么这个循环里不能同时持有 `&mut` 和 `&`？

**破坏实验：**
- 把 `&str` 参数改成 `String`，看调用处报什么错；
- 在持有一个引用的同时修改 `Vec`，触发 E0502，读 `rustc --explain E0502`；
- 把一个变量 move 进函数后再使用，触发 E0382。

**第 2 周周末，不借助 AI 的练习：** 自己手写一个函数，返回字符串切片中最长的单词。一开始不加生命周期标注，根据编译器提示修改，直到通过。

**通过标准：** 能不看资料讲清楚所有权的三条规则、借用的两条规则，以及 `String` 和 `&str` 的区别。

### 第 3～4 周：类型设计、trait、模块

**阅读：** 《The Rust Programming Language》第 10、13、17 章；《Rust for Rustaceans》第 1～3 章。

**让 AI 写：** 把项目拆成 workspace，建一个纯逻辑的 `domain` crate。**先自己设计类型，再让 AI 实现：**
- `ShortCode`、`UserId` 用新类型包装；
- 链接状态用 enum：`Active`、`Expired`、`Disabled`；
- 领域错误用 thiserror 定义。

**追问重点：**
- 这里用泛型 `T: Trait` 还是 `dyn Trait`？两者在编译产物、性能和灵活性上有什么区别？
- 这个 trait 为什么是 object safe（或者不是）？
- 为什么要实现 `From`？`?` 是怎么用上它的？
- `impl Trait` 出现在参数位置和返回值位置，含义有什么不同？

**破坏实验：**
- 给 trait 加一个泛型方法，看它还能不能作为 `dyn Trait` 使用；
- 删掉 `match` 的一个分支，体会穷尽检查怎么拦住遗漏；
- 把两个不同的新类型 ID 互相传错，确认编译器能发现。

**架构师专项：** 让 AI 用三种方式实现同一个仓储接口：泛型、trait object、enum 分发。对比代码量、编译时间、可读性，写一页取舍笔记。**这份笔记以后直接放进团队规范。**

**通过标准：** 能为一个新需求独立设计出类型和 trait 的签名，并说清楚每个选择的理由。

### 第 5～6 周：并发

**阅读：** 《The Rust Programming Language》第 16 章；《Rust Atomics and Locks》第 1～3 章。

**让 AI 写：** 一个后台线程池，定期扫描并清理过期链接，结果通过 channel 汇报给主线程。

**追问重点：**
- 为什么这里是 `Arc` 而不是 `Rc`？
- 为什么闭包要加 `move`？
- `Send` 和 `Sync` 分别保证什么？这个类型为什么自动实现了它们，或者为什么没有？
- `Mutex` 的 guard 什么时候释放？这里有没有死锁风险？
- 用 `Mutex`、`RwLock` 还是 channel？各自适合什么场景？

**破坏实验：**
- 把 `Arc` 换成 `Rc`，读懂 "`Rc<...>` cannot be sent between threads safely" 这个报错；
- 去掉 `move`，看借用检查器怎么报错；
- 在结构体里放一个 `Cell` 或 `RefCell`，看它为什么不再是 `Sync`；
- **故意写一个死锁**（两个锁、相反的加锁顺序），确认编译器**拦不住**。这能让你明白 Rust 并发安全的边界在哪里。

**通过标准：** 能解释 `Send`/`Sync` 的自动推导规则；能说出 Rust 能防止的并发问题（数据竞争）和防止不了的并发问题（死锁、逻辑竞态）。

### 第 7～8 周：异步和 Web 服务

**阅读：** tokio 官方教程；《Asynchronous Programming in Rust》；axum 和 sqlx 的官方示例。

**让 AI 写：** 用 axum + sqlx + PostgreSQL 实现短链服务的增删改查 API，带上超时和优雅停机。

**追问重点：**
- `async fn` 编译后变成了什么？为什么说 Future 是惰性的？
- 为什么 `tokio::spawn` 要求 `Send + 'static`？
- 为什么这里用 `tokio::sync::Mutex` 而不是 `std::sync::Mutex`？或者反过来？
- `Pin` 解决了什么问题？什么时候需要关心它？
- `select!` 里这个分支被取消时，会不会丢数据？
- axum 的 `State`、提取器（extractor）在类型层面是怎么实现的？

**破坏实验：**
- 持有 `std::sync::Mutex` 的 guard 跨越 `.await`，再 `tokio::spawn`，读懂 "future is not `Send`" 这个报错；
- 在 async 函数里调用 `std::thread::sleep`，压测时观察吞吐量的变化（编译器不报错，但服务会变慢）；
- 用 `cargo expand` 展开 `#[tokio::main]`；
- 故意写错一条 SQL，看 sqlx 在编译期报错。

**通过标准：** 能解释 `spawn` 为什么要求 `Send + 'static`；能看出一段异步代码里的阻塞调用和取消安全问题。

### 第 9 周：测试和可观测性

**让 AI 写：** 给服务补上单元测试、proptest 属性测试、insta 快照测试、基于真实数据库的集成测试；接入 tracing、metrics 和 panic hook。

**关键练习：**
- **用 cargo-mutants 审计 AI 写的测试**：跑一遍，看有多少"变异"没被测试发现，再让 AI 补测试；
- 制造一个慢查询，只靠 trace 定位问题，**不看代码**；
- 让 AI 只根据日志、trace 和指标排查一个你预先埋好的 bug，观察它需要哪些数据，以及在哪里卡住。

**通过标准：** 能判断一组测试是否有效；知道一个服务需要哪些可观测性数据，AI 才能有效排查。

### 第 10 周：所有权的极限

**阅读：** 《Learn Rust With Entirely Too Many Linked Lists》；slotmap 的文档。

**让 AI 写：** 链接依赖关系图（比如短链跳转链的检测）。分别用 `Rc<RefCell>`、arena + 普通索引、slotmap 三种写法实现。

**关键练习：**
- 在 `Rc` 版本里故意制造环，用工具观察内存泄漏；
- 在 arena 版本里删除节点后用旧索引访问，观察静默出错；换成 slotmap 后再看它怎么被检查出来；
- 读一段标准库或常用 crate 里的 unsafe 代码（比如 `Vec` 的部分实现），让 AI 逐行解释 `// SAFETY:` 注释保证了什么，再用 Miri 跑一个违反约定的例子。

**通过标准：** 能为图结构场景选出合适的写法并说明理由；能 review 一段 unsafe 代码的安全论证。

### 第 11～12 周：毕业项目，整理成团队模板

把项目整理成团队模板仓库：

- workspace 分层：`domain` / `app` / `infra-*` / `api` / `bin`；
- workspace 级别的 lint 配置、`rust-toolchain.toml`；
- CI：fmt、clippy、nextest、cargo-deny、cargo-machete；
- 可观测性接入；
- `CLAUDE.md`：把这 12 周里发现的"AI 常见错误"写成规则。

**最终检验：** 让 AI 在模板上实现一个新功能（比如访问统计），你只 review 不动手，记录每个问题的发现方式（编译器、lint、测试、还是靠人工 review）。**靠人工 review 才发现的问题，就是下一步要加进规则或类型设计的地方。**

## 四、追问模板（直接复制给 AI）

### 通用模板

```
下面是你刚写的代码。请逐处解释：
1. 每个 & / &mut / move / clone 的选择理由，换成另一种会怎样
2. 每个 Arc / Mutex / RefCell / Box 存在的原因
3. 每个显式的生命周期标注表达了什么约束
4. 每个 trait bound（尤其是 Send、Sync、'static）是被谁要求的
对每一条，给出"去掉它"会触发的编译错误码。如果某处其实可以去掉，直接指出。
```

### 复述打分模板

```
下面是我对这段代码的理解，请指出其中错误或不准确的地方，按 1～5 分打分，
并给出一个能检验我是否真正理解的反例或追问：
<你的复述>
```

### 出题模板（每周末用）

```
根据我这周学的 <主题>，出 5 道题：
- 2 道"这段代码能否编译，为什么"
- 2 道"修复这个编译错误，且不能用 clone 或 unsafe"
- 1 道设计题：给一个需求，让我设计类型和函数签名
先只给题，等我答完再给答案和讲解。
```

### 常用追问清单

| 主题 | 问题 |
|---|---|
| 所有权 | 这个值的所有者是谁？什么时候被释放？ |
| 借用 | 这个引用的有效范围到哪里？为什么这里不能同时有 `&mut`？ |
| 生命周期 | 返回值的生命周期和哪个参数绑定？省略规则是怎么推导的？ |
| 智能指针 | 为什么不能直接放在栈上？为什么需要共享所有权？ |
| trait | 为什么用泛型而不是 `dyn`？这个 trait 是 object safe 的吗？ |
| 并发 | 这个类型为什么是（或不是）`Send`/`Sync`？ |
| 异步 | 这个 Future 在哪些 `.await` 点可能被取消？取消时状态是否一致？ |
| 性能 | 这里有没有不必要的分配或复制？ |
| 设计 | 能不能用类型让这个错误在编译期就不可能发生？ |

**AI 说错的地方：** 无 / AI 说 xxx，实验证明不对。

## 六、几个容易踩的坑

1. **AI 的解释也会出错。** 遇到分歧，以编译器的行为和官方文档为准，这正是"破坏实验"的意义。
2. **不要满足于"因为借用检查器要求"。** 每个约束都要追问到"它防止了什么 bug"。
3. **不要跳过不用 AI 的练习。** 架构师要能判断 AI 写得对不对，自己完全写不出来，就判断不了。
4. **每阶段都要有产出。** 类型设计取舍笔记、并发规则、异步规则、模板仓库，学习过程同时就是团队规范的建设过程。
