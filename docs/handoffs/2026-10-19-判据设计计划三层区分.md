# 整合请求：判据、设计、执行计划三层区分

## 要解决的问题

kit 的 `claude/CROSS-PROJECT-REVIEW.md` 里同时出现"判据""设计""实施计划"三个词。目前的写法有：

- "审核方先派判据/任务"
- "执行方出设计和实施计划"
- 设计/计划评审请求包含"需求或收到的判据、成功标准、方案和取舍……实施步骤"

但三者各自该写什么、由谁定、在哪一关审，没有明确界定。用户确认，目前工作流把**设计和执行计划放在一起审核**。用户的 B 级任务由弱模型全程完成，基本都要返工一次。三层混在一起是可能的原因之一：

- 判据缺项，弱模型只能自己补。
- 设计评审和计划评审合在一起草草通过。
- 问题漏到实现阶段，表现为返工。

## 定义

三者回答三个不同的问题：

- **判据**：做成什么样才算对？
- **设计**：用什么方案做到？
- **执行计划**：按什么顺序、分几步做，每步怎么确认？

| | 判据 | 设计 | 执行计划 |
| --- | --- | --- | --- |
| 回答 | 什么算完成、什么算正确 | 结构怎么搭、为什么这样搭 | 先做什么后做什么，每步怎么验证 |
| 关注 | 结果（外部可观察的行为） | 方案（内部结构和取舍） | 过程（步骤、顺序、粒度） |
| 和实现的关系 | 和实现无关，换一种方案判据不变 | 选定一种方案 | 绑定这个方案的落地路径 |
| 必写内容 | 成功标准；边界情况；明确不做的事；验收方式 | 模块划分；接口与数据结构；关键逻辑；备选方案和取舍；影响范围；风险与降级 | 步骤拆分，每步写明改哪些文件、规模、验证命令；依赖顺序；回滚点；每步之后系统可用 |
| 谁来定 | 需求方或审核方 | 审核方或执行方（按级别） | 执行方 |
| 写错的后果 | 方向错，后面全错，而且验收也查不出来 | 方案不成立，或埋下维护和性能隐患 | 步子太大审不动；顺序错导致返工；中途状态不可用 |

## 例子：给登录接口加防暴力破解

**判据**（不提实现）

- 同一账号连续 5 次密码错误后锁定 15 分钟，锁定期间返回明确的错误码。
- 同一 IP 每分钟最多 20 次登录尝试。
- 正常用户输错一次再输对，不受任何影响。
- 不做的事：验证码、短信通知。
- 验收方式：自动化测试覆盖以上每一条；锁定到期后能自动解除。

**设计**（选定方案并说明理由）

- 计数放在 Redis（需要过期能力，也要扛住高频写）。
- 键设计为 `login_fail:{account}` 和 `login_rate:{ip}`，用 TTL 实现自动解锁。
- 在认证中间件里拦截，不改业务层。
- 取舍：Redis 不可用时放行，不拒绝。
- 影响范围：认证中间件和配置项，不碰用户表。

**执行计划**（逐步落地）

1. 配置项和 Redis 计数工具函数，附单元测试，约 80 行。
2. 中间件接入账号锁定逻辑，附集成测试（覆盖 5 次锁定和到期解锁），约 120 行。
3. IP 限流，附测试，约 60 行。
4. Redis 故障降级，附故障注入测试，约 50 行。

每一步都能单独提交、单独验证，做完任何一步系统都可用。

## 规则

1. **依赖方向：判据 → 设计 → 计划。** 评审从上往下：判据没对齐，就不审设计。验收从下往上：每一步按计划验证，最终结果按判据验收。
2. **判据里不写方案。** 比如"用 Redis 记录失败次数"属于设计。写进判据，等于把方案提前锁死；验收时检查的就变成"用没用 Redis"，而不是"有没有防住暴力破解"。判据只写外部可观察的行为。
3. **三层分开评审，各拦各的问题。**
   - 判据评审：拦目标偏差、缺项（边界、不做的事、验收方式）。
   - 设计评审：拦方案不成立、取舍不当、影响范围漏算、缺降级方案。
   - 计划评审：拦步子过大、缺验证步骤、顺序依赖错误、中途不可用。
4. **执行方遇到判据没覆盖的情况时，先问，不要自己补。** 弱模型自行补全判据，是"不是我要的"这类返工的主要来源。

## 判据模板

判据模板是派单时必须填写的固定栏目。它不规定判据写什么内容，只规定判据必须回答哪些问题。

写判据最常见的问题不是写错，而是**漏写**。强模型脑子里默认的东西（边界怎么处理、什么不做、做到什么程度算完）没写下来，弱模型只能猜，猜错就是一次返工。模板把"应该想到的问题"固定成栏目，空着的栏一眼就能看出来。这和门禁是同一个思路：用清单逐项判定，不依赖写判据的人记得周全。

```text
【目标】一句话：解决谁的什么问题
【成功标准】可观察、可判定的行为，逐条编号
【边界情况】异常输入、并发、空值、上限、失败路径各怎么表现
【不做的事】本次明确不做的，防止范围扩大或执行方自作主张
【约束】不能改的东西：接口兼容、性能指标、依赖、项目约定、允许改动的范围
【验收方式】每条成功标准怎么验证：哪些测试、什么命令、看什么结果
【未决问题】写判据时还没想清楚的，标明由谁、何时定
```

| 栏目 | 防的是 |
| --- | --- |
| 目标 | 理解偏差：做对了一件不是你要的事 |
| 成功标准 | 验收无法判定，各说各的 |
| 边界情况 | 漏测边界：正常路径通了，异常路径崩了 |
| 不做的事 | 范围偏移：顺手多做，或擅自砍掉一部分 |
| 约束 | 方案碰了不能碰的东西 |
| 验收方式 | 执行方自己定标准自己验 |
| 未决问题 | 没想清楚的地方被藏起来，执行方只能自己补 |

**填好的例子**（登录接口防暴力破解）：

```text
【目标】防止对登录接口的密码暴力破解，同时不影响正常用户
【成功标准】
  1. 同一账号连续 5 次密码错误，锁定 15 分钟，返回错误码 ACCOUNT_LOCKED
  2. 同一 IP 每分钟超过 20 次登录尝试，返回 429
  3. 输错 1 到 4 次后输对，正常登录，并清零计数
【边界情况】
  - 锁定期间输入正确密码：仍然拒绝
  - 锁定到期：自动解除，不需要人工干预
  - 账号不存在：同样计数，返回和密码错误相同的提示，避免账号枚举
【不做的事】验证码、短信或邮件通知、管理后台的解锁按钮
【约束】登录接口的请求和响应格式不变；P99 延迟增加不超过 10ms
【验收方式】自动化测试覆盖成功标准 1–3 和全部边界情况，审核方在同一棵 tree 上重跑
【未决问题】阈值是否做成可配置：产品下周给结论，本期先写在配置项默认值里
```

"账号不存在"这一条，强模型知道怎么处理，但容易觉得太显然而不写；弱模型多半想不到账号枚举的问题。模板的作用就是逼着写判据的人把这类内容写下来。

**模板在三个环节起作用：**

1. **派单时**：任何一栏为空都不派出。确实不适用的栏写"无"，表示想过了。
2. **执行时**：执行方遇到判据没覆盖的情况，先问，不要自己补。
3. **验收时**：按成功标准和边界情况逐条核对，按验收方式重跑。结论引用条目编号，例如"2 不通过：超限返回了 500 而不是 429"，返工内容因此变得具体。

**模板会逐步扩充。** 每次验收不通过都记下原因类别。某类原因反复出现、而现有栏目防不住时，就加一栏，或在某栏下加一个必答子问题。例如：

- 多次因为没考虑并发而返工：在"边界情况"下固定加一问"并发或重复提交时怎么表现"。
- 多次因为改了不该改的文件而返工：在"约束"下固定加一问"允许改动的范围"。

模板就是踩过的坑的积累。

## 设计与计划分段评审

**现状的问题**：设计和计划放在一起审，会出现三种情况。

- **注意力被计划吸走。** 计划写得具体（步骤、文件、行数），看起来扎实；而设计层的问题，比如方案是否成立、取舍、降级、影响范围，容易被放过。
- **只有一个结论。** 看不出问题出在哪一层；返工时往往只改了计划，设计的毛病还在，到实现阶段才暴露。
- **计划白写。** 设计一旦不成立，基于它写的计划要整份重写。

**做法一（推荐默认）：一次提交，两段评审，设计不过就不看计划。**

1. 先对照判据审设计：方案能否满足每条成功标准、各边界情况怎么处理、取舍和降级是否写明、影响范围是否算全。
2. 设计不通过就直接退回，**不审计划**，结论写明"设计层不通过"。
3. 设计通过后再审计划：每步能否单独验证、规模、顺序依赖、每步之后系统是否可用。

结论分两行写，例如：

```text
设计：通过
计划：需修订（第 2 步过大，缺验证命令）
```

这样返工原因天然就按层归类了，retro 可以直接统计。

**做法二：分两次提交，先交设计，通过后再写计划。**

设计文档短，审一轮的成本远低于实现返工一轮。在 B 级几乎每单返工一次的现状下，用一次便宜的设计往返换掉一次昂贵的实现返工，大概率划算。可以只对涉及跨文件判断逻辑、并发、状态机、数据结构变更的 B 级任务启用做法二，其余用做法一。

**试行建议**：接下来 5–10 单 B 级任务按做法一执行，记录以下三项：

- 首次验收通过率
- 设计层退回占比
- 总耗时和成本（和以往对比）

试行后按结果判断：

- 设计层退回多：对复杂任务启用做法二。
- 设计很少退回、返工仍多：问题更可能在判据或验收测试，应优先落实判据模板，拆分评审帮助不大。

## 和返工原因分类的对应

《强弱模型分工的验收防线》第 4 条提出给验收不通过的原因分类。下表把每类原因对应到最早应该拦住它的那一层，用来判断该收紧哪里：

| 返工原因 | 应在哪一层拦住 | 改进动作 |
| --- | --- | --- |
| 判据缺失、理解偏差 | 判据 | 补判据模板的必写项；判据交由用户或审核方确认 |
| 方案不成立、取舍不当 | 设计 | 收紧设计评审，必须写备选方案和降级 |
| 漏测边界、范围偏移 | 计划 / 验收测试 | 计划里每步写验证命令；验收测试由审核方先定 |
| 钻判据空子 | 判据 + 验收测试 | 判据写"不做的事"；执行方不得修改验收测试 |
| 风格、约定不符 | 计划（引用项目约定） | 派单时附上相关约定，交付前自检 |

## 成功标准

- 全局规则中能查到三层的定义、必写内容和评审职责，并且和现有 A/B/C 分级、B 级"执行方出设计和计划、审核方评审"的流程不矛盾。

- 试行期能统计出首次验收通过率、设计层退回占比、总耗时和成本。
