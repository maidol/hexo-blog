# 整合请求：交付粒度（让人审得动）

级别：B（只改文档，由 drsg-harness-kit 决定落点和措辞）
来源：hexo-blog 会话里与用户讨论"review 耗时接近自己写，用 agent 的意义何在"时得出的结论，用户要求提交给 kit 整合。

## 要解决的问题

如果人审一份 agent 改动的时间和自己重写差不多，就失去了交给 agent 的意义。审不动，多半是因为一次交上来上千行、目的混杂的大改动，而不是审的人慢。

## 要点（原文总结）

1. **先讲方案，再动手。** 非小改动先交方案，用户只审方案；实现按批准的方案验收。
2. **拆成小步提交。** 每步只有一个目的，可以单独验证。审一个 50 行、目的清楚的改动，比审一个大杂烩快得多。
3. **每步附"我怎么验证的"。** 写清跑了什么、结果如何、哪些没验证。
4. **单步上限：变更不超过 400 行。** 这条出自用户团队的《研发管理规范 V2.0》4.4 节，原本针对人提的 MR，对 agent 同样适用。

## 建议落点

`claude/AGENT-EFFICIENCY.md` 新增一节（全局，适用于所有项目）。建议文本如下，可按 kit 的风格改写：

```markdown
## 交付粒度：让人审得动

- 人审改动的时间接近自己重写，交给 agent 就白费了。审不动多半是粒度问题：一次交上千行、几件事混在一起。
- **先讲方案，再动手。** 跨多个文件、改接口或数据结构、改判断逻辑的改动，先给方案（要解决什么、改哪几处、取舍、怎么验证），确认后再写。用户审方案，实现按方案验收。
- **一步一个目的。** 每次提交只做一件可单独验证的事；搬迁/重命名和行为改动分开提交。单步变更不超过 400 行（不算生成文件、lockfile、纯搬迁），能几十行就几十行。
- **每步附「我怎么验证的」。** 跑了什么命令、结果、覆盖了哪些情形、没验证什么。
- 确实拆不开（如一次性迁移），先说明原因，并给审阅顺序：先看哪几个文件、哪些可以略过。
```

## 和现有内容的关系（请整合时核对，避免重复）

- `claude/CROSS-PROJECT-REVIEW.md` 已有 A/B/C 分级：C = 预计不到 100 行、单模块。B 级要先出设计和计划给审核方评审。本条的"先讲方案"面向的是**人**审方案，和"审核方项目评审"是同一思路的两种场景，可以互相引用。
- `claude/MAIN-BRANCH-WORKFLOW.md`「实现改动要能分开」讲的是工作区里不同时挂两个功能的改动。本条讲的是单个功能内部再拆步。两者不冲突。
- 400 行这个数字要不要写死，还是写成"项目有约定按项目约定，没有默认 400 行"，由 kit 决定。

## 成功标准

- 全局规则里能找到这几条：先方案后实现、小步提交、每步附验证说明、单步规模上限。
- 和 C 级"不到 100 行"、B 级计划评审的表述不矛盾。
- 如果 kit 有文档覆盖检查（`tests/check-docs-coverage.sh`）或中英双份（`docs/en`、`docs/zh`），一并同步。
