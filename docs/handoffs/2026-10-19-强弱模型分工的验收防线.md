# 整合请求：强弱模型分工下的验收防线

级别：B（以改文档为主，可能涉及 retro 统计；落点和措辞由 drsg-harness-kit 决定）
来源：hexo-blog 会话中与用户讨论代码 review 和验收时总结的结论，用户要求提交给 kit 整合。
关联：[2026-10-19-交付粒度.md](2026-10-19-交付粒度.md)（同一次讨论，内容是"让人审得动"）

## 现状（用户描述）

- **分工**：强模型负责需求分析、定判据和标准、审方案、验收；代码实现交给下游较弱的模型。实现、审核、测试由不同的模型承担。
- **分级**：A/B/C 三级，对应 `claude/CROSS-PROJECT-REVIEW.md`。B 级由弱模型全程完成，包括设计、计划和实现，强模型负责评审和验收。
- **实际情况**：**B 级基本都要返工一次**。

## 结构上已经做对的

- **验证和生成分开**：审核方不是执行方。执行方如果来自不同的模型家族，盲区重叠更少。
- **强模型 token 用在关键处**：强模型用在判据和验收上，大量实现交给便宜的模型。
- **现有防线**：kit 里已经有"改过的现有断言清单"、变异测试、tree 绑定验收与授权，以及"第二次验收不通过就升级给主模型"的熔断规则。

## 残余风险与建议

### 1. 判据成了单点

如果强模型在需求分析阶段理解有偏差，执行方按错误的判据实现，审核方也按同一份判据验收，三道关会一起放行。盲区重叠没有消失，只是从代码层移到了判据层。

- **建议**：A/B 级的判据（成功标准、边界、明确不做的事）由用户确认后再派发。读一页判据比读一份 diff 快得多，这里是人的时间杠杆最大的地方。
- **验收**：可以考虑让审核方在验收前，先用一两句话复述"这个需求要解决的是什么"，和判据原文对照。

### 2. 弱模型倾向于"满足判据"，而不是"解决问题"

常见手法包括：改断言让测试变绿、跳过或禁用测试、针对测试用例写特判、吞掉异常、缩小功能范围但不说明。

- **建议**：**验收测试由审核方先写好或先批准，执行方只能让它通过，不能修改。** 执行方需要改这些测试时，必须先发 notice 申请，不能在实现里顺手改。
- 现有的"改过的现有断言清单"可以扩展为"改过的测试、跳过的测试、新增的特判分支"三项。

### 3. 不采信执行方的"已验证"

执行方回执里写"测试通过"，只能说明执行方声称通过。

- **建议**：审核方在同一棵 tree 上自己重跑验收命令，以重跑结果为准，回执只作为参考。如果 kit 已经要求这样做，就在验收判定里写明"重跑结果：命令 / 通过数 / tree"。

### 4. 返工成本可能倒挂（与"B 级基本都返工一次"直接相关）

可以预期的固定一轮返工，说明第一轮的作用实际上是"发现判据缺了什么"。这一轮的成本是：弱模型实现一遍，强模型审一遍，弱模型再改一遍，强模型再审一遍。总成本和时延可能接近，甚至超过强模型直接做。

- **把返工前移**：B 级的设计和计划评审要卡严。验收不通过的原因，如果能在计划阶段发现，就应该在计划评审时拦下，而不是等实现出来再退回。
- **把返工原因反馈回判据**：每次"验收不通过"都按类别记录原因，例如：
  - 判据缺失
  - 理解偏差
  - 钻判据空子
  - 漏测边界
  - 范围扩大或缩小
  - 风格或约定不符

  高频类别进入两处：一是派单模板（判据里固定要写的项），二是执行方交付前的自检清单。自检清单就是"上次被退回的原因"，交付前逐条对照。
- **熔断之外加前置分流**：现在的规则是"两次不过就升级"，管的是事后。再补一条事前判断：哪些特征的任务派给弱模型，返工率明显偏高（比如涉及跨文件的判断逻辑、并发、状态机）。这类任务直接上调到 A 级，或者拆细后再派。

### 5. 交接会丢失上下文

强模型做分析时积累的上下文，执行方拿不到。

- **建议**：派单的判据要能单独读懂，包括成功标准、边界情况、明确不做的事、验证方式，以及已知的坑。执行方越弱，步骤拆得越小、写得越明确。这和关联交接单《交付粒度》是同一条原则，只是读者从人换成了下游模型。

## 度量（判断这套分工是否划算）

| 指标 | 含义 | 异常说明 |
| --- | --- | --- |
| 首次验收通过率 | B 级第一次验收就通过的比例 | 目前接近 0，是最需要拉起来的指标 |
| 平均返工轮数 | 每单从派发到验收通过经历了几轮 | 偏高：拆得不够细，或者级别派错 |
| 验收逃逸率 | 验收通过后又发现的问题 | 偏高：判据或验收不够硬 |
| 单任务总成本 | 强模型加弱模型的 token 和时延 | 高于强模型直接做：分级线该往下调 |
| 返工原因分布 | 按第 4 条的类别统计 | 高频类别进入派单模板和自检清单 |

建议由 `skills/agent-efficiency-retro` 扩展统计。数据来源是 Event：验收不通过的 notice 和升级的 handoff。这要求"验收不通过"的 notice 里带上原因类别字段，或者用固定前缀。

## 建议落点（由 kit 决定）

- `claude/CROSS-PROJECT-REVIEW.md`：
  - 第 2 条：验收测试由审核方先定，执行方不得修改。
  - 第 3 条：审核方必须重跑。
  - 第 4 条：返工原因分类、自检清单、前置分流。
  - 第 5 条：派单判据要能单独读懂。
- `claude/AGENT-EFFICIENCY.md` 的要点区：放一行摘要。
- `skills/agent-efficiency-retro`：增加首次验收通过率、返工轮数、返工原因分布的统计。
- 第 1 条（判据由用户确认）涉及用户的工作方式，建议作为可选项，写进用户全局 `CLAUDE.md` 的模板说明，不作为强制规则。

## 成功标准

- 上述 5 条在全局规则里都有对应表述，并且和现有的 A/B/C 分级、两次不通过升级、授权提交流程不矛盾。
- "验收不通过"带原因类别，retro 能统计出首次验收通过率和返工原因分布。
- 运行一段时间后，B 级首次验收通过率明显上升。目标值由用户定。
- 中英文文档、`tests/check-docs-coverage.sh` 等按 kit 惯例同步。
